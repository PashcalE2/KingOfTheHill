# Царь горы

Это аддон который идейно копирует одноименный режим в шутерах.


## Правила

На карте есть так называемые "**ключевые точки**", захват которых важен для одержания победы.

Все эти правила являются **дискуссионными** -- они лишь первоначальная версия без участия в игре живых людей.


### Условие победы

Каждая команда начинает с одинаковым количеством **очков победы**:
1. Каждую секунду, для каждой команды -- за каждую захваченную **ключевую точку** отнимается `1` **очко победы**.
2. Когда счетчик доходит до `0` -- команда побеждает. 
3. Если одновременно счетчик достигает `0` для обоих команд -- победа засчитывается обеим.
    * Пример как это можно поднастроить иначе -- кикнуть из игры остальные команды и добавить оставшимся дополнительные **очки победы**.


### Ключевые точки

Это ентити класса `critical_point`, которые могут иметь следующие состояния:
1. Ничья -- начальное состояние.
2. Захватывается -- ничья И есть захватчики ОДНОЙ КОМАНДЫ.
3. Борьба -- ничья И есть РАЗНЫЕ захватчики:
    * захват приостановлен;
    * игрой считается, что `CaptureTeamId == 0`, так как не понятно, кто захватывает;
    * та команда, которая осталась после борьбы, продолжает захват.
4. Восстановливается -- НЕ ничья И есть владельцы И нет захватчиков ВОЗМОЖНО РАЗНЫХ КОМАНД:
    * прогресс захвата восстанавливается до `1`.
5. Под защитой -- НЕ ничья И есть владельцы И есть захватчики ВОЗМОЖНО РАЗНЫХ КОМАНД:
    * прогресс отхвата приостанавливается.
6. Отхватывается -- НЕ ничья И есть захватчики ВОЗМОЖНО РАЗНЫХ КОМАНД.
7. Захвачена -- НЕ ничья И на точке пусто.


## Идеи организации аддона

Первоначально, я решил разделить обязанности между кусками програм с помощью создания различных SENT (ScriptedENTity). Этот метод показался мне более удобным чем разделение по lua-модулям (`module(...), require(...)`) в плане запуска на своей локалке (не требуется перезапуск сервера для обновления аддона).

Недавно заметил относительно классную штуку:
```lua
-- game_manager/init.lua
-- глобальная переменная видна в прочих файлах проекта
KOTFPlayers = {}
```

Кажется, она очень плоха тем, что эта переменная становится доступна для других аддонов (например LuaPad). Я не против пользоваться такой фичей, поэтому когда кто-то будет это смотреть - обратите вниманеия на такие "глобальные" переменные и не удивляйтесь, почему я могу их использовать в прочих файлах.

## Как это происходит на сервере

Вообще, ради повышения безопасности и общей стабильности -- я бы ЗАПРЕТИЛ спавнить и удалять любые ентити из этого аддона КЕМ УГОДНО, кроме самого СЕРВЕРА. И вот почему:
1. Общая проблема -- их можно случайно удалить:
    * нажав UNDO;
    * если другой админ, через E2 / starfall / ... решит выпендриться и почистит что-то определенное, и случайно этим чем-то окажутся эти ЖИЗНЕННО ВАЖНЫЕ ентити;
    * ВАЖНО! При ПОЛНОЙ ОЧИСТКЕ карты -- ничего ужасного не произойдёт, так как все энтити удаляться одновременно, а не с большими промежутками времени в порядке UNDO (`game_manager` в последнюю очередь) / случайным образом.
2. `game_manager` -- я подразумевал, что одновременно может существовать только 1 ентити этого класса на сервере. Обратите внимание, что хук на прослушку чата создаётся при создании этой ентити, и удаляется при её удалении. При удалении именно этой ентити происходит возвращение игроков в начальное состояние (например их цвет) и возвращение аддона в ~первоначальное состояние. Если же подразумевать работоспособность одновременно нескольких ентитей, то будут такие проблемы:
    * будет более сложное хранение информации, необходимой для аддона (что наверно не является невозможным, но в чем смысл, если количество игроков в первоначальной игре не ограничено?);
    * будет более сложное управление остальными ентити (надо будет настраивать их принадлежность определенной "игре").


### Подготовка

0. Удалите вызов `createRandomTestCase()` в [game_manager/init.lua](lua/entities/game_manager/init.lua) (иначе все игроки будут участвовать).
1. Ставим `game_manager` ОДИН РАЗ (если поставили случайно второй - удаляйте оба, возможно пофикшу).
    - После удачного спавна одной ентити -- появится хук на чат.
2. Ставим `critical_point` -- можно несколько штук.
3. Взаимодействие с чатом.

В чат можно писать кучу команд, сейчас не вспомню все, но вот несколько:
1. `/join <teamName>` -- записать себя в команду (указывать команду не обязательно, тогда игрок запишется в рандомы).
2. `/start_game` -- запустит жизненно важные процессы для точек и менеджера игры.
3. ...


### Критические точки

Перед запуском игры, необходимо заспавнить `critical_point`. Можно спавнить сразу несколько.

В ентити хранятся net-переменные (`<тип>` -- `<слот>` -- `<имя>` -- `<назначение>`):
1. `Float` -- `0` -- `CaptureProgress` -- значение от `0` до `1`, где: `0` -- точка ничья; `1` -- кем-то захвачена.
2. `Int` -- `0` -- `OwnerTeamId` -- числовой идентификатор команды, которая сейчас владеет точкой. Если `0`, то точка ничья.
3. `Int` -- `1` -- `CaptureTeamId` -- числовой идентификатор команды, которая сейчас захватывает точку. Если `0`, то рядом с точкой не вражеских команд.
4. `Int` -- `2` -- `Status` -- числовой идентификатор статуса точки (см. правила).


### Счетчики очков победы

При запуске игры, сервер спавнит ентити `win_score_counter` для каждой команды.

В ентити хранятся net-переменные:
1. `Int` -- `0` -- `TeamId` -- перед началом игры, аддон назначает числовые идентификаторы каждой команде. Можно было бы сделать строчки, но если кому-то когда-то захочется погнаться за производительностью -- сравнивать 32-битные целые чиселки проще чем сравнивать строки.
2. `Int` -- `1` -- `WinScore` -- аддон будет отнимать целые числа из этого значения по правилам игры.

Изначальное количество очков регулируется в [win_score_counter/shared.lua](lua/entities/win_score_counter/shared.lua)
